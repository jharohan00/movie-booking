# Agents.md — AI Workflow Documentation

This file documents the AI-assisted development workflow used to build the Movie Ticket Booking System.

## AI Tools Used

- **Google Antigravity (Antigravity IDE)** — Primary AI coding assistant (Claude Sonnet 4.6 with thinking)

## Workflow

### Phase 1: Problem Decomposition & Planning

The first step was creating a detailed implementation plan artifact covering:
- Tech stack choices and rationale
- Full domain model with all entities and relationships
- Complete API surface (endpoints, roles, HTTP methods)
- Key design decisions (two-phase booking, pessimistic locking, refund policy priority chain, async notifications)
- Open questions and trade-offs

The implementation plan was created as an artifact and submitted for user approval before any code was written.

### Phase 2: Structured Code Generation

Code was generated in dependency order to avoid forward references:

1. **Foundation** — `pom.xml`, `application.yml`, Flyway migrations (V1–V4)
2. **Domain enums** — 8 enums (Role, SeatType, ShowSeatStatus, etc.)
3. **JPA Entities** — 13 entities (City → Theater → Screen → Seat → Movie → Show → ShowSeat → User → PricingTier → DiscountCode → Booking → BookingItem → Payment → RefundPolicy → Notification)
4. **Repositories** — 14 Spring Data repos with custom JPQL (including pessimistic lock queries)
5. **Security** — JwtUtils, JwtAuthenticationFilter, UserDetailsServiceImpl, SecurityConfig
6. **Config** — JpaAuditingConfig, AsyncConfig, OpenApiConfig
7. **Exceptions** — 5 custom exceptions + GlobalExceptionHandler
8. **DTOs** — 11 request DTOs + 7 response DTOs
9. **Services** — AuthService, CityTheaterService, MovieShowService, PricingService, BookingService, PaymentService, RefundPolicyService, NotificationService
10. **Events & Schedulers** — BookingConfirmedEvent, BookingCancelledEvent, BookingEventListener, HoldExpirySweeper, ReminderScheduler
11. **Controllers** — 7 controllers (AuthController, 4 Admin, 2 Customer)
12. **Tests** — 3 unit test classes (BookingService, PricingService, RefundPolicy) + 3 integration test classes (Auth, BookingFlow, Concurrency)
13. **Documentation** — README.md, Agents.md

### Phase 3: Design Decisions Made with AI Assistance

The AI was asked to make and document the following design decisions:

#### Concurrency Safety
**Decision**: Use `SELECT … FOR UPDATE` (JPA `@Lock(PESSIMISTIC_WRITE)`) on `ShowSeat` rows.
**Reasoning**: The requirement explicitly excludes distributed systems, so DB-level locking is the correct approach. Locks are acquired in ascending ID order to prevent deadlocks. The alternative (optimistic locking with retries) was considered but rejected because the failure-and-retry pattern creates poor UX and complex retry logic.

#### Notification Delivery
**Decision**: Store in DB + log via SLF4J. Use `@Async` + `ApplicationEventPublisher`.
**Reasoning**: Keeps notification delivery non-blocking (booking flow is never held up by notification I/O). A real email/SMS provider would replace the `log.info` lines without changing the architecture. A message broker (RabbitMQ/Kafka) was considered but excluded as out of scope.

#### Refund Policy Priority
**Decision**: Show-level > Theater-level > Global default.
**Reasoning**: More specific policies always override broader ones. Admins can set global defaults and override per-theater or per-show.

#### Payment Gateway
**Decision**: Mock service with configurable failure rate (default 0%).
**Reasoning**: No real provider needed for a take-home. The interface (`PaymentService`) is structured so a real gateway (Stripe, Razorpay) can be swapped in by implementing the same method signatures.

### Phase 4: Iterative Refinement

The AI was used to:
- Catch missing entity fields (e.g., `@Version` on `ShowSeat` for optimistic lock baseline)
- Identify potential LazyInitializationException issues and add `JOIN FETCH` in JPQL queries
- Ensure correct transaction boundaries (all seat-state transitions happen inside `@Transactional`)
- Write comprehensive unit and integration tests

## Key Learnings

1. AI excels at generating boilerplate-heavy JPA entities and Spring Boot configuration.
2. The most value came from AI reasoning about **concurrency** (choosing pessimistic vs optimistic locking, deadlock prevention via ID ordering) and **architecture** (event-driven notifications, two-phase booking).
3. Generating tests alongside code (not after) produced better coverage and caught issues earlier.
